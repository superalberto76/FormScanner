# FormScanner — HTTP API

This document describes the rules that apply across the FormScanner API: authentication, access, conventions, errors, review concurrency, uploads, served images and exports, with a map of the resources. The reference of every endpoint, with its parameters and schemas, is the OpenAPI document generated by the backend.

## 1. Reference

A running backend serves:

| URL | Content |
|---|---|
| `/docs` | Swagger UI: every endpoint, its parameters and schemas; requests can be tried after signing in with "Authorize" |
| `/redoc` | The same reference, as a document |
| `/openapi.json` | The OpenAPI document, for generating clients |

The OpenAPI document is generated from the code (routes, Pydantic schemas, docstrings), so it always matches the running version. This document does not repeat it.

## 2. Conventions

- **Base path:** `/api/v1`. With `docker-compose.yml`, `http://localhost:8000/api/v1`.
- **Format:** JSON in and out, except uploads (`multipart/form-data`) and downloads (PDF, CSV, XLSX, images).
- **Identifiers:** UUIDs.
- **Times:** ISO 8601, always in UTC.
- **Enums:** upper-case strings (`DRAFT`, `MATCH_FAILED`…), listed in [data-model.md](data-model.md#7-enums).
- **Partial updates:** `PATCH` changes only the fields sent.
- **Aggregates** (counts of readings to review, missing pages, score during review, readiness for scanning and export) are computed on every read; the client never computes them itself.
- **Review rules are the server's:** each reading of the review read carries `confirmable` and `bulk_acceptable`; clients use these flags instead of deriving them.
- **Actions on a submission in review return the whole review page** (`SubmissionReviewDetail`), so the client replaces its copy with the answer instead of patching it.
- **No pagination**, except the audit log (`limit`, at most 500, and `offset`).

## 3. Authentication

1. `POST /api/v1/auth/login` with `{"email": "...", "password": "..."}` returns `{"access_token": "<jwt>", "token_type": "bearer"}`.
2. Every other request, except `GET /api/v1/health`, sends `Authorization: Bearer <jwt>`.

The token is an HS256 JWT signed with `JWT_SECRET`, with the user id (`sub`), the system role and the expiry; it lasts `ACCESS_TOKEN_EXPIRE_MINUTES` (480 by default). There is no refresh token: when it expires, the client signs in again.

| Situation | Response |
|---|---|
| Wrong email or password, or a disabled account, at login | `401` |
| Missing, invalid or expired token | `401` with `WWW-Authenticate: Bearer` |
| Valid token of an account disabled since | `403` |

Passwords: an administrator creates a user, or resets a password, with a temporary password, and the user's `must_change_password` becomes true. The client then sends the user to `POST /api/v1/auth/change-password`, which in that state does not ask for the current password; otherwise it does. The server does not block other requests while `must_change_password` is true. The password policy (length and character classes) is in the schema of the endpoint.

`GET /api/v1/auth/me` returns the signed-in user; `PATCH` updates the profile (names, theme).

## 4. Access

- **System role.** `ADMIN` manages users (`/api/v1/users`), acts on every project as an owner would, without being a member, and reads the whole audit log. `USER` sees the projects they are a member of and the audit rows of their own actions.
- **Project membership** (`OWNER` or `COLLABORATOR`) decides access to a project and everything under it: variants, pages, objects, batches, submissions, images. A non-member gets `403`, a resource that does not exist `404`.
- **Owner (or administrator) only:** changing the project's status (`POST /form-projects/{id}/transition`), managing members, deleting the project. Every other operation is open to all members.
- **State gates.** Authoring (variants, pages, objects) needs the project and the variant in `DRAFT`; batches and uploads need the project `ACTIVE` and ready for scanning; review needs the submission `SCANNED`, whatever the project's status. A refused state is a `409`. The rules are in the [functional specification](functional-specification.md).

## 6. Errors

| Status | When | `detail` |
|---|---|---|
| `401` | Not signed in (section 3) | Text |
| `403` | Not allowed: not a member, not an owner, not an administrator, account disabled | Text |
| `404` | The resource does not exist (or is not under the parent in the path) | Text |
| `409` | The request conflicts with the state of a resource | Text, or an object (below) |
| `413` | Upload too large (section 8) | Text |
| `415` | Upload of an unsupported type | Text |
| `422` | Invalid request: FastAPI's validation errors (a list), or a rule of the service (text) | List or text |

**Structured 409.** When the client has to react differently to different conflicts, `detail` is an object: `{"code": "...", "message": "...", ...}`. `code` is the contract; `message` is for people and can change. The codes:

| `code` | Raised by | Extra fields |
|---|---|---|
| `NOT_REVIEWABLE` | Lock or review save on a submission that is not `SCANNED` | `status` |
| `LOCK_LOST` | Review save while another user holds the lock | `locked_by`: `{user_id, display_name, locked_at}` |
| `SUBMISSION_CHANGED` | Review save, "Review anyway" or reopen based on an older version | `current_version` (review save, reopen) |
| `NOT_CONFIRMABLE` | Confirm of a reading that cannot be confirmed | `reason`: `NO_READING`, `EMPTY_IDENTIFIER`, `INCOMPLETE_IDENTIFIER`, `IDENTIFIER_TOO_LONG`, `NOT_DECODED` |
| `NOT_RESOLVED` | Undo on a reading with no decision | — |
| `NOT_ELIGIBLE` | "Review anyway" on a submission that does not allow it | `reason`: `STATUS` (with `status`) or `NOT_EXTRACTED` |
| `EXTRACTION_RUNNING` | Extraction, "Review anyway", a threshold change, or closing or reopening a submission, while an extraction run holds the batch | — |
| `NOT_SCAN_READY` | Batch creation or upload when the project's published variants are not ready for scanning | `published_variant_count`, `colliding_variant_ids` (when two variants share an identifier value) |
| `INVALID_STATUS` | Variant assignment, "Mark unresolvable" or its undo from a state that does not allow it; reopening a submission that is not `REVIEWED` | `status` |
| `VARIANT_NOT_PUBLISHED` | Assignment of a variant that is not `PUBLISHED` | `variant_status` |
| `NOT_EXPORT_READY` | Results export of a batch that is not ready | `to_extract`, `in_review`, `to_assign`, `unassigned` |
| `OBJECT_IN_RESERVED_BAND` | Creating an object, or moving or resizing it, into the reserved bands of the page | `page_index` |
| `OBJECTS_IN_RESERVED_BANDS` | Publishing a variant with objects in the reserved bands | `objects`: `[{id, label, object_type, page_index}]` |

Every other `409` has a text `detail`.

## 7. Review concurrency

Several users can review the same batch. Two mechanisms, both per submission, keep them from overwriting each other.

**Lock.** `POST /submissions/{id}/lock` is called when the submission is opened and periodically while it stays open. If the lock is free, expired or already the caller's, the caller gets it (`acquired: true`); if someone else is active on it, the response is still `200`, with `acquired: false` and who holds it. The lock expires after **15 minutes** without activity (opening, renewing or saving). `POST …/lock/take-over` takes it from whoever holds it; it is the only way to free a lock held by someone else. `DELETE …/lock` releases it on exit. Only the holder can save: another user's save gets `409 LOCK_LOST`.

**Version.** The review read returns `review_version`. Every review save sends the version it was based on and, when admitted, increments it; a save based on an older version gets `409 SUBMISSION_CHANGED` and the client reloads. Review saves are: a decision on a reading (`POST …/results/{result_id}/review`), editing the candidate (`PATCH …/candidate`), "Accept all remaining" and closing. Reopening also sends the version of the closed submission.

A decision on a reading has the body:

```json
{"action": "CONFIRM", "review_version": 7, "note": "optional", "value": null}
```

`action` is `CONFIRM`, `SUBSTITUTE`, `FLAG` or `UNDO`. `value` is required with `SUBSTITUTE`, in the shape of the reading's type (see the OpenAPI schemas `QuestionSubstitution`, `MatrixSubstitution`, `FreeTextSubstitution`, `CodeSubstitution`, `RespondentIdentifierSubstitution`). The server computes the validity of a substituted value. Confirming or substituting the respondent identifier also sets the submission's candidate.

## 8. Uploads

All uploads are `multipart/form-data`. The type of a file is always taken from its content, never from its name or declared type. The backend reads at most the size limit plus one byte, so an oversize file is refused without being read entirely.

| Endpoint | Field | Accepted | Size limit | Refusals |
|---|---|---|---|---|
| `POST /submission-batches/{id}/pdf-uploads` | `file` (one PDF) | PDF; one upload is one submission | `MAX_SUBMISSION_PDF_BYTES` (50 MiB) | `413`; `422` not a readable PDF |
| `POST /submission-batches/{id}/image-uploads` | `files` (one or more) | JPEG, PNG | `MAX_SUBMISSION_IMAGE_BYTES` (20 MiB) per file | A file too large, empty or of another type is listed in `rejected` and the others are ingested |
| `POST /page-objects/{id}/image` | `file` | PNG, JPEG, BMP, SVG | `MAX_IMAGE_UPLOAD_BYTES` (10 MiB) | `413`; `415` other types; `422` empty file, or an SVG that cannot be parsed safely |
| `POST /auth/me/avatar` | `file` | as above | as above | as above |

Both scan uploads return `201` and need the project `ACTIVE` and ready for scanning (`409 NOT_SCAN_READY` otherwise). They run matching before answering. The order of the files in an image upload is kept: it is the fallback order of the sheets. How images are grouped into submissions and ordered is in the [functional specification, §5.5](functional-specification.md#55-grouping-sheets-into-submissions). SVG files are sanitized before they are stored ([architecture.md](architecture.md#7-file-storage)).

## 9. Served images

| Endpoint | Image |
|---|---|
| `GET /page-objects/{id}/image` | The picture of an IMAGE object (`404` if none was uploaded) |
| `GET /auth/me/avatar`, `GET /users/{id}/avatar` | A profile picture |
| `GET /submission-pages/{page_id}/image` | A scanned sheet: the straightened image if the sheet was aligned, otherwise the original scan |

All of them need authentication, so a browser loads them with an authenticated request and shows them through an object URL. The `Content-Type` comes from the content of the file, and every response has `X-Content-Type-Options: nosniff`. Pictures and profile pictures are also served with `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`, so an SVG cannot run scripts even if opened directly. Sheet images have a weak `ETag` with `Cache-Control: private, no-cache` and answer `304` when unchanged.

## 10. Downloads

| Endpoint | Parameters | Content |
|---|---|---|
| `GET /form-variants/{id}/export/pdf` | `mode`: `STUDENT` (default) or `SOLUTION`; `filename` (optional) | The printable PDF of the variant (see [pdf-export.md](pdf-export.md)), as an attachment |
| `GET /submission-batches/{id}/export/summary` | `format`: `xlsx` or `csv`; `csv_dialect`: `comma` (default, `.` decimals) or `semicolon` (`,` decimals) | One row per submission |
| `GET /submission-batches/{id}/export/detail` | as above | One row per submission, with the columns per object |

The results exports need the batch ready for export (`409 NOT_EXPORT_READY` otherwise) and read the batch in one consistent snapshot. Their content, columns and file names are in the [functional specification, §10](functional-specification.md#10-results-export).
